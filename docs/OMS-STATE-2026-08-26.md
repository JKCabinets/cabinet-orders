# 1. The shape of the thing

A Shopify storefront (`jkcabinets2you.com`, **not yet live**) and a custom
order-management system (`ordersjkcabinets2you.com`). Next.js 16, Supabase,
Kamal → Docker → one Hetzner box. Small internal team, Queen Creek Arizona,
`America/Phoenix` throughout.

**No staging environment.** Every deploy goes straight to production.

## ⚠ The OMS is no longer entirely behind auth

Added 2026-09-08. Two endpoints answer anonymous requests from the storefront:

| Route | For | Writes? |
|---|---|---|
| `POST /api/public/lookup` | "where is my order" | no |
| `POST /api/public/claims` | the warranty claim form | yes |

⚠ **Everything under `app/api/public/` is unauthenticated BY CONSTRUCTION.**
`proxy.ts` exempts the directory, not the files, so adding a route there makes
it public with no second decision anywhere. That is the point of the directory
and also the hazard.

⚠ **Both run as the SERVICE ROLE**, like every route on this box — full table
access, RLS bypassed. The `public_api` role with narrow column grants was
designed to be the real boundary and **does not exist**. Until it does, the
explicit select list in each route is the only thing keeping `customer_phone`,
`ship_to` and `internal_notes` out of a public response. Treat those select
lists as a security control.

⚠ **They fail in opposite directions, deliberately.** The lookup's rate limiter
fails CLOSED: a Redis outage letting reads through turns it into an order
number oracle. The claims intake fails OPEN: refusing a claim during an outage
costs a customer their claim, inside a window Terms 12.3 makes a condition
precedent. Spam is recoverable; a missed deadline is not.

**⚠ EVERY ACTION IS A PILL** (Garrett, 2026-10-07). Anything a person presses —
a button, or a link that acts like one — is pill-shaped like the rest of the
OMS: `rounded-full`, a thin border, a faint fill, small uppercase letters. Plain
underlined text is too easily missed. Use the styles already in the screens,
verbatim: the terracotta pill for the main action (`bg-terracotta/20 border
border-terracotta/45 text-terracotta`), the cream-bordered one for an ordinary
action (`border-cream/18 bg-white/4`, as the attachments panel's Upload), and
the neutral one for the rest (`bg-white/5 border-cream/20`). An action never
sits inside another clickable thing: a card that opens something keeps its
actions in a row of their own.

# 2. ⚠ The data model — read this before anything else

## A checkout is a PROJECT. Its lines split into GROUPS.

This is the single most important thing to understand, and the thing most older
documents get wrong.

```
projects           one row per Shopify checkout
  └── orders       one row per PRODUCT CATEGORY in that checkout
```

One customer buying cabinets and a sample produces **one project and two
`orders` rows** — a cabinets group and a samples group. Each has its own stage,
its own SLA clock, its own timeline. A project whose cabinets are in production
while its samples are delivered is **normal**, and any summary that flattens
those into one status is hiding the thing the model exists to show.

Splitting is by **line-item vendor**, per line, in `lib/categories.ts`. An
unmatched vendor falls through to `order` deliberately, so the line lands in a
queue somebody works, and it is logged.

⚠ **Older text saying "a sample is an order whose every line is the sample
vendor, mixed orders are standard" describes the pre-project model and is
wrong.** It appears in more than one place.

⚠ **THIS MODEL DECIDES THE PUBLIC LOOKUP.** One project can have cabinets in
production and samples already delivered at the same time, so a lookup cannot
return one status. The customer-facing contract lives in OPERATIONS §2.

## Five types

| `type` | What it is | Has a project? |
|---|---|---|
| `order` | Cabinets | yes |
| `hardware` | Hardware | yes |
| `sample` | Samples | yes |
| `custom` | Quote-form or manual job | **no — standalone** |
| `warranty` | Claim about a purchase | **no — standalone** |

That project/standalone split decides three things: **archiving**, **claiming**
and **money**. See §3.

⚠ **A `warranty` row is standalone but never orphaned.** `about_order_id` is
required and points at the **GROUP** it is about — `SHO-1050-CAB`, not
`SHO-1050` — because the 48-hour reporting window in Terms 12.3 runs from a
delivery, and deliveries are per group. `reported_at` carries the customer's
submission time, not the row's creation time.

## Order numbers

Customer sees `ORDER #1050`. The OMS project is `SHO-1050`. Its groups are
`SHO-1050-CAB`, `SHO-1050-HW`, `SHO-1050-SMP`. Shopify's internal id is never
customer-facing. Custom jobs keep a `QUO-` prefix, which encodes origin rather
than type.

**Warranty claims are `WRN-1050-1`, `WRN-1050-2`.** Added 2026-09-08. Generated
in one place, `lib/warrantyId.ts`.

⚠ **The sequence is per PURCHASE, not per group.** `SHO-1050-CAB` and
`SHO-1050-SMP` both key on `1050` and share one sequence, so a claim on the
cabinets and a claim on the samples are `-1` and `-2`. `lib/createWarranty.ts`
counts by id pattern for that reason; counting by `about_order_id` would give
both `-1` and leave the conflict retry to notice.

⚠ **The suffix is ALWAYS present, even on the first claim.** If `-1` were
implicit, every consumer would have to handle two shapes, and the second claim
on an order is exactly when somebody discovers it.

⚠ **Every claim is its own row.** Two claims on one order are independent: each
has its own dates and lead times regardless of when it was raised. Same
reasoning as cabinets and samples being separate groups under one project,
applied one level down.

## ⚠ A customer submission is a DRAFT, not a claim

Added 2026-09-08. `claim_submissions` holds what a customer sent through the
website. It is **not** a row in `orders`, has no id, no stage of its own and no
SLA clock.

It appears on `/warranty` above the claims table, at `New claim` — which is what
that stage means: nobody has worked it yet. A team member opens it, confirms
which GROUP it is about, and records what actually needs replacing. Creating the
claim is that act, and it produces the `warranty` row.

**Both records are kept.** The customer says "my base drawer cabinet has a dent
in the drawer front"; a vendor cannot fill that. Staff write "W1842-580F-PN,
Middle Drawer Only, qty 1". The submission is what they actually reported,
`received_at` carries legal weight under Terms 12.3, and editing a report in
place is how the report gets lost.

⚠ **Drafts are never shaped into `Order` objects.** The orders hub feeds its
rows to the table, the bulk action bar, the modal and the stage-move path. A
draft wearing an `Order`'s shape would reach all four, and a bulk stage advance
would be advancing something that has no row.

**A manual claim is the same screen with nothing prefilled** — for a mistake on
JK's side needing a replacement, where there is no customer report to work
from. One flow, one create path, one id sequence.

⚠ **THE PUBLIC ENDPOINT, AS OF 2026-10-01.** `POST /api/public/claims` answers
the website's contract of that date (`website-to-oms-open-items-2026-10-01.md`,
section 1). The page sends in the background and READS the answer, so: CORS for
both storefront hosts on every answer; Cloudflare Turnstile first, on the claims
widget's OWN secret (`TURNSTILE_CLAIMS_SECRET_KEY`), requiring the action
`claim` and a storefront hostname, so a quote-form token fails here; and 201
with `{"ref": "CR-1042"}`. The page acts on exactly 400 `turnstile_missing`,
403 `turnstile_failed`, 429 and 503 `turnstile_unavailable`; anything else shows
the customer the email route, and an email inside the window counts as the
report. Every other refusal carries a machine key in `error`, the sentence in
`message`, and the file or field where one is the cause (2026-10-07):
`form_unreadable` 400, `field_invalid` 422 with `field`, `too_many_photos` 422,
`photo_too_large` 413 and `photo_unreadable` 415 with `file`,
`photos_too_large_total` 413, `rate_limited` 429, `save_failed` 500.

⚠ **REQUESTS REACH THE APP WHOLE UP TO 64 MB, AND NO FURTHER** (2026-10-07).
`proxy.ts` runs on every route, and Next buffers each body for it up to
`experimental.proxyClientMaxBodySize` in `next.config.mjs` — 10 MB by default,
and a longer body is CUT OFF, not refused: the route cannot read the form and
answers 400. Until 2026-10-07 that broke every claim over 10 MB (a 15 MB one
did, in production), every quote over 10 MB (they allow 50) and every staff
upload over 10 MB (they allow 20). Now 64 MB, which clears a claim's six 10 MB
photos; the claims route refuses a larger request with 413
`photos_too_large_total` before reading it. The two numbers must stay equal:
`CLAIM_MAX_REQUEST_BYTES` in `lib/claimIntake.ts`. kamal-proxy adds no limit of
its own (`--max-request-body` is unset, so unlimited).

- **The reference** is `ref`, generated from an identity column: CR-1001
  upward. "CR", not a WAR- number: no claim exists until a person promotes the
  submission, and a reference that looked like one would be a promise not yet
  made. Promotion puts it in the claim's notes, so a call quoting it finds the
  claim.
- **The spam checks FLAG; they do not drop** (Garrett, 2026-10-01). A filled
  `website` honeypot or a send within two seconds sets `screening` and the
  submission stays at `new`, shown in the queue with the reason. They used to
  answer a fake success and store nothing; a browser autofilling a field called
  "website" would have cost a real customer their reporting window. Turnstile
  runs before them, so whatever reaches them has proven itself. A honeypot flag
  keeps what the field contained, first 100 characters (`screening_value`,
  2026-10-05): the first genuine claim from the live page, CR-1003, was flagged
  because Chrome's autofill filled the field, and "filled" alone could not tell
  a company name from a bot's junk.
- **Photos are scrubbed before they are stored** (`lib/stripExif`): location,
  camera and text out of JPEG and PNG, a JPEG's Orientation kept. Until
  2026-10-01 claim photos were stored exactly as they arrived.
- **Every claim becomes a Help Scout conversation, AFTER it is recorded**
  (2026-10-05, `lib/claimHelpScout.ts`). The OMS first — checked, scrubbed,
  stamped, referenced — then Help Scout, where the team answers: if Help Scout
  is down the claim is already safe, `pending`, and a 15-minute job sends it
  (`/api/cron/helpscout-sync`, check `helpscout-sync`). Built to the website's
  specification: tag `oms-claim`, subject `Claim received, reference CR-1042`,
  the customer as the conversation's customer, type `email`, no auto reply, the
  form's labels and plain punctuation in the first thread, and an internal note
  for the team. `helpscout_state` on each submission is `pending`, `sent` or
  `skipped` (every row from before); `claim_helpscout_lease()` is the only way a
  sender gets one, so the immediate send and the job never send a claim twice,
  and a sender searches the inbox for the reference before creating anything.
- **The OMS sends the customer nothing.** The confirmation email is the
  WEBSITE's Help Scout workflow, which finds claim conversations by the tag;
  every human reply goes through Help Scout (OPERATIONS §10).
- **A submission is claimed like an order** (2026-10-06): `claimed_by` holds
  the `team_members.id`, set only by `claim_submission()` and
  `begin_promotion()`; release is the owner's alone, as `release_order()`.
  The triage card says who has it and does not open for anyone else.
  **Promoting claims it first, and leases it:** `begin_promotion()` claims the
  submission for the promoter and takes a five-minute lease in one locked
  step, so neither a colleague nor a second press can promote it again while
  one promotion runs. The new warranty claim belongs to the promoter.
- **Claims that arrive by EMAIL are entered by staff** (2026-10-06): "Claim
  from an email" on the warranty band, `POST /api/claim-submissions`. Typed by
  hand — nothing is read out of the email — including when the email arrived
  (Arizona time, exact: UTC-7 all year), which is the report date the claim is
  judged against; it cannot be in the future, and `entered_by` records who
  entered it. Photos: JPEG or PNG only, checked and scrubbed exactly as the
  public form's, in `lib/claimIntake` — ONE copy of those steps, the public
  route's answers proven unchanged. The Help Scout link is checked to be a real
  conversation in inbox 373175, and a unique index holds ONE CLAIM PER
  CONVERSATION. The entry is claimed by whoever made it. `source` is `website`
  or `email`; an emailed claim's push ADOPTS its conversation — subject set,
  `oms-claim` added to the tags it has, the note — and never creates one.
- **A warranty claim's progress reaches its conversation as internal notes**
  (2026-10-07). The trigger `orders_claim_helpscout_note` queues every warranty
  row's creation and every change to its `stage` — whatever made it: a person,
  a tracking number advancing it — into `claim_helpscout_notes`. The PATCH
  route and promotion send a claim's queue at once, unawaited;
  `/api/cron/helpscout-sync` sweeps whatever is left. `claim_helpscout_note_
  lease()` hands out only a claim's OLDEST pending note, so notes land in the
  order things happened, and a failed one holds the claim's later ones back. The
  conversation is the one its submission was sent to: a claim logged by hand,
  or from a submission older than the push, has none and is `skipped` (after
  ten minutes — promotion names the claim on its submission just AFTER creating
  it). A note says the stage, from where, when (Arizona time), who has the
  claim, and the tracking number when it ships. ⚠ The trigger runs as whoever
  updates `orders`, so `service_role` is granted on the queue outright.
- **Deleting a warranty claim CLOSES its conversation — never deletes it**
  (2026-10-07). The BEFORE DELETE trigger `orders_claim_helpscout_close` reads
  the claim's conversation while the row still exists and queues a `deleted`
  event carrying it (`order_id` null, `claim_ref` the number); the sender adds
  a last internal note saying so, then sets the status to Closed. A reply
  reopens it, as Help Scout always does. The same trigger UNLINKS the claim's
  submission (`promoted_to_order_id` is plain text, no foreign key) and says
  so in its review notes: `createWarranty` numbers a claim as the highest
  existing number plus one, so a deleted claim's number is reused, and a
  dangling link would have sent the new claim's notes to the OLD customer.
  The lookup takes the most recent promotion, never `maybeSingle()`. A
  conversation deleted IN Help Scout is skipped with its reason, not retried.

# 3. The five pipelines

⚠ **Stage names are NOT globally unique.** `New` and `Delivered` appear in
several flows; `In review` is in both warranty and custom; **`Shipped` is in
three**. Always resolve against the row's `type` — never by searching arrays
blind. This has caused real incidents.

| Flow | Stages |
|---|---|
| **Cabinets** | New → Entered → In production → At cross dock → Delivered |
| **Hardware** | New → Ordered → Shipped → Delivered |
| **Samples** | New → Shipped → Delivered |
| **Custom** | New → In review → Ordered → In production → At cross dock → Delivered |
| **Warranty** | New claim → In review → Parts ordered → Shipped → Resolved |

**How each moves:**

- **Cabinets.** New → Entered is human, gated on a manufacturer acknowledgment
  or an attachment. Entered → In production is automatic when a production start
  date is set. In production → At cross dock is the `production-complete` cron,
  its sole owner. At cross dock → Delivered is human and **gated on a signed
  proof-of-delivery attachment**, overridable with a logged reason.

  ⚠ **Both overrides take a reason and write an activity row** (2026-09-15).
  The control is accountability, not permission: anyone may override, and
  everyone can see who did. `override_ack` was a bare boolean that wrote
  nothing — no reason, no name, no trail — for the whole of its life until
  then, and OPERATIONS §10 had recorded the inconsistency as known-wrong.

  ⚠ **The flag also used to sit INSIDE the gate's condition**
  (`&& !body.override_ack`), so an override skipped the check entirely: a
  row whose acknowledgment was green recorded a bypass of a check that
  would have passed. The check runs first now, and the reason is consulted
  only when it actually fails.

  ⚠ **"An acknowledgment" means a GREEN one that still describes the order.**
  Added 2026-08-27. Every acknowledgment stores a fingerprint of exactly what
  the reconciliation compared — normalised customer name, normalised ship-to,
  and per-SKU quantities and modifications. The gate recomputes it and a
  mismatch blocks the advance: a confirmation of lines that have since changed
  is not a confirmation of this order.

  ⚠ **THE UI NAMES THE AUTOMATIC MOVE** (2026-09-15). A row In production with
  an estimated finish date says so — "Moves to At cross dock on 09/18/2026,
  when production ends" — and its button reads **Manual Push**, because
  pressing it takes the transition early rather than being the only way
  forward. `lib/autoAdvance.ts` holds the cron's rule and BOTH import it: a
  promise made where the cron will not keep it is worse than silence, because
  somebody waits for it. Without a finish date the cron's query never matches,
  so the row sits indefinitely and the wording stays neutral.

  ⚠ **Entered → In production is GATED on a production start date.** Added
  2026-09-08. Setting the date auto-advances the row, and that used to be the
  whole rule — nothing refused a manual advance without it, so a row could
  reach In production where `production-complete` could never move it, because
  that cron advances on `production_est_finish_date <= today`.

  The manufacturer gives dates within a day or two of the order being placed,
  well before production starts, so a row here without them is a skipped step
  rather than an honest unknown. The gate accepts the date in the same request
  as the stage, because that is what the modal sends.

  ⚠ **A stale acknowledgment does NOT move an order backwards.** If a customer
  amends an order that has already advanced, the row stays where it is and asks
  for a fresh acknowledgment. Reverting a stage as a side effect of a phone call
  is not a decision the system should take.

  ⚠ **The gate is LOOSER than the wording suggests, and that is DECIDED.**
  The server passes on a green acknowledgment **or any attachment at all** —
  the file need not be an acknowledgment. Kept loose deliberately
  (2026-09-08): HCI and J&K change their order forms constantly, so a parser
  for them would be a gate that breaks on somebody else's schedule. The
  in-app wording names both remedies. `OPERATIONS` §12 carries the reasoning.
- **Hardware and samples.** ⚠ **A TRACKING NUMBER IS WHAT MAKES A GROUP
  "Shipped"** — not a button. Entering one in the modal advances it; so does a
  Shopify fulfilment carrying one. One rule, both doors. Delivered stays a human
  action: nothing tells us a parcel arrived. Clearing a number does not move the
  row back.

  ⚠ **But a backward move CLEARS the number.** Added 2026-08-27. The number is
  the evidence for "Shipped", so a row sitting before that stage cannot hold it
  — and while it did, the SLA clock stayed off for exactly the row that needed
  chasing, because that clock runs on the number being absent.
- **Custom.** Hand-driven end to end. Dates are typed in after a phone call and
  nothing automated reads them. **No receipt gate on At cross dock →
  Delivered** (2026-09-09): a custom job runs on the customer's own contract
  and purchase order, so Terms 12.3 does not reach a custom job and the signed
  proof of delivery that evidences it is not required. Both copies of the
  gate ask `lib/requirements`, whose custom block is the record of this.

  ⚠ **More generally: a custom job has no gates at all** (2026-09-09). It is
  an organisation tool, and its dates are a record of a phone call rather
  than a condition of anything. **That applies to the UI too** — no control
  may withhold itself pending a custom date and no copy may say one unlocks
  a step. Three did until 2026-09-09, all at At cross dock, and a demand
  nothing enforces is worse than a gate: there is no refusal to search for,
  only a button that never appears.

**Shipping reality:** cabinets go by freight to a cross dock (**no tracking
number, ever**). Hardware is drop-ship — placed with the manufacturer, who ships
direct and supplies the tracking number. Samples ship from JK's own stock,
usually same day, and **their label is bought inside Shopify**, so the Shopify
fulfilment is the primary door for a sample's tracking number.

⚠ **Whether a HARDWARE tracking number ever reaches Shopify is undecided.** It
depends on the vendor and on whether they are integrated with it. "Ships via
UPS" and "the fulfilment carries real carrier and tracking" were written into
`lib/categories.ts` as fact on 2026-08-25 and were assumptions; the comments now
say so. No hardware product is live, so nothing has tested any of it.

## ⚠ One truth per item

Stated once, because it now decides several behaviours. **The row holds the
current truth; the activity log holds the history.** A backward move clears
whatever the stage it returns to will demand again, so re-entry is always a
fresh recording — even when the value is identical, because what is recorded is
a new decision rather than the same one twice. Anything worth keeping for
documentation goes in attachments or internal notes; the OMS does not accumulate
every version of a fact.

## ⚠ Dates: stored ISO, displayed MM/DD/YYYY

Added 2026-09-15. The DATE columns — `production_start_date`,
`production_est_finish_date`, `scheduled_delivery_date` — are stored ISO and
rendered through `formatMDY` in `lib/dates.ts`.

⚠ **IT PARSES THE STRING RATHER THAN USING `new Date()`.** These are DATE,
not timestamp: `new Date("2026-09-16")` is UTC midnight, which in Phoenix is
5pm on the 15th, so every date in the app would render a day early and look
like a data fault.

⚠ **`orders.date` AND `order_activity.time` ARE NOT ISO.** They are stored as
DISPLAY strings ("Sep 14"), written that way at ingest, so they still read
that way and `formatMDY` returns them untouched. Making them consistent means
changing what is written, not the renderer — and `order_activity.time` having
no clock component is also why the pipeline rail cannot show per-stage
timestamps.

The corollary is the activity log's guarantee: **every PATCH records everything
it changed.** Not one row per field — a stage move caused by a date is one row
describing both — but nothing changes silently, and nothing is claimed that did
not happen.

## Ownership, archiving, money

**One owner per PURCHASE.** A project is claimed as a whole, so a designer who
has finished the cabinets is not blocked from closing it while somebody else
sits on the hardware. Custom jobs and warranty claims are claimed individually,
having no project. Claiming happens on `/projects` or the work queue, never from
a stage table — a Claim button on a cabinet row would quietly take the samples
too.

⚠ **A CLAIM IS ENFORCED, NOT DISPLAYED** (2026-09-15). Until then it was
shown in three places and checked in none: any signed-in member could move,
date, annotate or upload against a row somebody else had claimed. A claim
that only shows an avatar does not do the one thing claims exist for.

`requireOrderClaim` in `lib/auth.ts` is the single answer, called by the
PATCH route, attachment upload, attachment delete and acknowledgment upload.
Unclaimed is open — claiming is how you take a row, and requiring one before
any edit would make every first touch a two-step. Another member's claim is
refused with 409 `claimed_by_other`.

⚠ **ADMINS ARE EXEMPT UNCONDITIONALLY, AND THE GUARD LOGS IT.** The modal's
"Edit order" toggle is deliberateness in the UI, not enforcement — an
admin's request succeeds whether or not it has been pressed. Do not "fix"
the server to require it: an admin acting through the API, a script or a
stale tab must still be able to act, and must still land on the activity
trail.

⚠ **THE OVERRIDE ROW IS WRITTEN ONLY IF THE CHANGE SUCCEEDS** (2026-09-16).
The guard used to insert it the moment it let an admin through, and every
caller can still stop after that — eleven refusals below the guard in the
PATCH route, and a failed write in all four callers — so each of those left
"Edited by X (admin) while claimed by another member" on the trail for an
edit that never happened. Now `requireOrderClaim` only *records* the override
on a per-request `ClaimOverrideLog`, and `withClaimOverrideLog`, which wraps
each of the four route handlers, writes it when the response is a 2xx. The
log is required by the guard and exists only inside the wrapper, so an
unwrapped caller does not compile — nobody has to remember. On success the
row follows the edit's own activity rows rather than preceding them.

⚠ **OWNERSHIP RESOLVES THROUGH THE PROJECT.** `orders.claimed_by` is null on
every project-linked row since the claim moved up on 2026-08-25, so a check
reading it raw finds no owner on any Shopify purchase — it would enforce
nothing on the type with the most hands on it.

**Archived as a whole purchase**, and only once every group reaches the last
stage of its own flow, or the purchase is refunded. A refund is an ending.
The terminal-stage rule is enforced in `app/api/projects/[id]`, which refuses
with `not_complete` and names the unfinished groups.

⚠ **THE PROJECT IS THE ONLY TRUTH FOR ARCHIVING — decided 2026-09-15,
enforced 2026-09-16 (`76115c7`).** `orders.archived` stays false on project-linked rows; a group
is hidden because its PROJECT is archived, resolved by lookup. Writing both
is two copies of one fact. `PATCH /api/orders/[id]` refuses `archived` in
either direction on a project-linked row with 422 `archived_not_allowed`,
naming the project, and `/api/orders/bulk` refuses each such row the same
way. `/api/orders/archive`, a third order-level path that nothing called,
was deleted rather than given a refusal.

The refusal sits above the claim guard in the PATCH route because it is a
statement about the row, not about who is asking. It was also placed there
while the guard still wrote its override row immediately; since 2026-09-16
that row is written only on success, so the placement no longer matters for
the trail.

**The UI follows through one question: `archivesAsOrder` in `lib/data`.**
The modal's Archive/Restore button, the table's Delivered action and the
bulk bar all ask it, so none of them offers one group of a purchase on its
own. The modal's button also needs the viewer to be able to act on the row,
matching the table. The store's `archiveOrder` reverts a refused change and
returns the server's reason; it used to discard it, which left the row gone
from the board until a refresh.

⚠ **A COLUMN REACHES THE BROWSER ONLY IF `shapeOrder` MAPS IT.** It copies
`orders` field by field, and an optional field on the `Order` type that the
mapper skips is `undefined` in every browser while the column is full — and the
compiler says nothing, because optional is optional. It happened to
`custom_specs` and `quote_submission` on 2026-09-25 and was found on 09-28: the
preferences panel rendered nothing, and the specs panel opened empty on a job
that had specs, where a Save would have written the emptiness back. **Adding a
column the client reads is two edits, and only one of them is enforced.**

**A CUSTOM JOB IS SPECS AND FILES** (2026-09-25). `orders.custom_specs` holds
AREAS (Kitchen, Master Bath), each with one or more SETS (Perimeter, Island),
each set carrying one manufacturer, one door style, one colour and notes — so a
kitchen whose island differs from its perimeter is two sets under one area. Areas
and sets carry generated ids, and `order_attachments.spec_ref` points at one, so
a file belongs to the job, an area or a set. An upload is filed under one by
`spec_ref` on `POST /api/orders/attachments` (2026-09-30): custom jobs only,
ordinary files only, refused unless the job's STORED specs have that room —
`specRefResolves` in `lib/data` is the one reading of a ref. A room removed
between that check and the insert leaves the file reading as the job's: ids are
never reused. A room's bin is what sends one (handoff item 24, step 4).
Deleting an area or set UNLINKS its
files; files change often and losing a drawing to a renamed room is the worse
failure. ⚠ Nothing did that until 2026-09-30, though this paragraph said so; the
room functions below now do it in the same transaction as the removal. The
document carries `v`, so a future shape is recognisable rather than guessed at —
`v: 2` since 2026-09-30, when every area gained `rev`.

**SPECS ARE SAVED ONE ROOM AT A TIME, AGAINST THAT ROOM'S REVISION** (2026-09-30).
`CustomSpecsPanel` renders in the modal for custom jobs only, keyed by the job.
Each room saves, and is removed, on its own through `POST /api/orders/[id]/specs`
— custom jobs only (422 `custom_specs_not_allowed`) — which keeps every guard the
other write routes have (archived read-only, the claim, the admin-override row
on success only) and calls `custom_specs_save_area`
or `custom_specs_remove_area` (`migrations/2026-09-30-custom-specs-rooms.sql`).
Each LOCKS THE ROW, compares the revision the caller loaded with the room's `rev`,
merges that one room, and clears `spec_ref` on the files of anything removed — one
transaction, because PostgREST has none of its own. A stale save gets 409
`specs_conflict` carrying the stored room. Saving Kitchen never conflicts with
saving Bath. One trail row per room saved, added or removed.

⚠ **WHAT THIS REPLACED WAS NOT WHAT THIS SECTION SAID.** Until 2026-09-30 it
described per-room saves that made concurrent edits "a visible conflict", and an
unknown version that "becomes empty" as a protection. Driven against the real
component that day: "Save room" sent the WHOLE document, every room's unsaved
typing with it; a refused save reverted every room; a removed room could not be
saved on its own; nothing compared anything, so the last write won; and PATCH
stored whatever `readCustomSpecs` made of the body — for an unknown version or
`null`, an EMPTY document. The panel also read its job once: handed a second
job, it saved the first job's rooms onto the second. That one was LATENT — every
page closes the modal before opening another job — and is closed by the key.

⚠ **PATCH REFUSES `custom_specs`** — 422 `custom_specs_moved`, before it reads
anything — rather than ignoring the field, which would answer 200 to a tab still
running the old panel for a save that never happened.

⚠ **THE DATABASE HOLDS EVERY WRITER TO IT.** `orders_custom_specs_valid` admits
only a valid v2 document — `custom_specs_problem()` says what is wrong: known keys
only, `a_`/`s_` ids unique across the document, text fields, `rev` a whole number
from 1, at most 100 rooms of 50 style groups. `orders_custom_specs_custom_only`
keeps specs off every other type. `readCustomSpecs` is the lenient RENDERER: it
copies field by field, so a field it does not name is invisible in every browser,
and every document the validator accepts reads back through it unchanged.

⚠ **THE VALIDATOR IS service_role-ONLY, AND RLS IS WHY THAT IS ENOUGH.** A role
without EXECUTE on a CHECK's function cannot write ANY row of the table, not only
one with specs. `orders`' policies (`no_direct_insert/update/delete`, false for
public) leave `service_role` and the table owner as its only writers. A policy
that ever opens writes to another role must grant that role the validator too.

A refusal that is not a conflict — the network, somebody's claim — keeps the
room's typing on screen, marked "Unsaved changes"; a conflict replaces it with the
stored version and says so. Removing a room asks first; its files stay on the job.

⚠ **NO GATES ON A CUSTOM JOB.** A designer owns it end to end: no acknowledgment,
no delivery proof, no admin PIN. SLA still applies, and a claimed job shows in My
Work.

**A QUOTE SUBMISSION IS THE CUSTOMER'S REQUEST, NOT THE DESIGNER'S RECORD**
(2026-09-24). `orders.quote_submission` (jsonb) holds the website form's payload
as it arrived: stable keys with the words the customer read beside them, both
multi-selects, the form version and the file metadata. Written once at ingest;
nothing in the OMS updates it. `orders.submission_id` carries the form's own id,
unique where present, so a retried submission returns the first job instead of
opening a second.

⚠ **THE CUSTOMER NOTE CARRIES THE CUSTOMER'S OWN MESSAGE, AND NOTHING ELSE**
(2026-09-28). The quote webhook used to write the whole submission into `notes`
as prose — name, phone, address, the budget KEY, the raw door_style array — and
`notes` is the field shown as "visible to the customer, written to the Shopify
order" (only where there IS a Shopify order, since 2026-10-05; a custom job or
a claim says it is kept in the OMS) and the one a designer writes their message
in. It now stores only what
the customer typed in their own notes box. Everything else is in
`quote_submission`; the rows written before were cleared by
`2026-09-28-clear-quote-prose.sql`, which keeps their message and leaves
pre-capture rows alone, since for those the prose is the only copy.

**THE REQUEST IS SHOWN BELOW THE RECORD** (2026-09-25). `QuoteSubmissionPanel`
renders `quote_submission` under the specs on a custom job: preferred door styles
and colours as chips, budget, project type, home type, timeline, their notes and
the names of the files they attached. It shows the LABELS the customer read, not
the stable keys — `$10,000 to $25,000`, never `10k_25k` — and it offers no
control at all, because a record you can edit is not one. A job raised by hand
has no submission and the panel renders nothing.

⚠ **A NEW VALUE IN A CONSTRAINED COLUMN IS TWO CHANGES.** `order_attachments.kind`
has a CHECK listing what it accepts. Code that wrote `customer_upload` shipped on
2026-09-28 without extending that list, so every customer upload was REJECTED for
two days: the file reached storage, the row did not, and the Files pane showed
nothing. Before writing a new value, read what the column allows —
`select pg_get_constraintdef(oid) from pg_constraint where conrelid =
'public.order_attachments'::regclass and contype = 'c'`.

**A FILE SAYS WHO PUT IT THERE** (2026-09-28). `order_attachments.kind` is
`general`, `proof_of_delivery` or `customer_upload`, and every view of an
order's files shows the same bins: **Designer attachments** (the job's own —
receipts included with their badge, and anything filed under a room that no
longer exists), **Customer attachments** (what arrived with a quote request),
and on a custom job **one per room** (2026-10-01), a style group's files in its
room's bin, tagged with the group. `attachmentBin` in `lib/data` decides the bin
for every view, and a custom job's Files tab IS the attachments panel, so the
bins cannot drift apart. Uploading in a room's bin files the upload under that
room; the modal's own pickers always file under the job. Customer offers no
upload — a customer's file is something that arrived, not something staff add.
⚠ The quote webhook set NO kind at all before
this, so those rows took the column default and sat among the designer's
drawings; the value is written at ingest and never inferred afterwards, because
`general` on an older row genuinely could be either. A customer's claim photos
are `customer_upload` too, since 2026-10-01: promotion filed them as `general`
until then, and that day's migration moved the rows it had written.

⚠ **ONE LIST, WHATEVER SHOWS IT** (2026-09-30). `lib/attachments` holds an
order's files for every view: the panel and the modal's Files tab read the same
list, so an upload or a delete in one is in the other. Every request takes a
ticket and only the newest may write, so a slow answer that set off before a
change cannot land on top of it. A view mounting refetches — attachments do not
publish over realtime (§5), and that is how a colleague's upload appears. A
delete leaves the screen only when the server has done it, and a failed load
says so instead of reading as "no files". The panel is read-only on somebody
else's claim as well as on an archived row, and offers **Receipt** only where
`lib/requirements` ever asks for one — cabinet groups. `lib/stageGates` still
asks the server at the moment of a move: a gate must not read a cache.

⚠ **NOTHING PARSES THE NOTES PROSE ANY MORE** (2026-09-28). `QuoteInfoPanel`
read the "QUOTE REQUEST" text out of `notes` with a regex per label and rendered
the form's raw keys. It also replaced the customer-note TEXTAREA on quote jobs,
so the designer who owns the job could not write a customer note on it. Gone: the
note is a field again on every row, and the customer's answers come from
`quote_submission` in their own words. Nothing writes the prose any more either:
the webhook stopped the same day (the customer-note paragraph above). This
sentence said otherwise until 2026-09-30.

⚠ **THE DESIGNER'S FIELDS STAY EMPTY UNTIL A DESIGNER FILLS THEM.** The form
sends PREFERENCES — several door styles, several colours — and those belong in
the submission. `door_style` and `color` on the row are the SELECTION, made after
talking to the customer. Writing the preference list into them made a wish look
like a decision, which is what happened to the first real submission on
2026-09-24.

⚠ **AN ACTIVITY ROW IS DATED IN PHOENIX** — `activityDate()` in `lib/data`
(2026-09-16). The server's clock is UTC, so a row written after 5pm Phoenix
without a timezone carried TOMORROW's date and the trail said work happened on
a day it had not. Eleven writers already passed `America/Phoenix`; the PATCH
route, the admin-override row, the warranty route and the client's optimistic
label did not, and now call the helper. Rows written before this keep the date
they were given: which of them are wrong cannot be told from the row.

⚠ **AN ARCHIVED ROW IS READ-ONLY** (2026-09-16). The archive is history: it is
browsed and restored, not worked. `lib/archived.ts` answers the one question —
archived on its own, or through its purchase — and six write paths ask it:
`PATCH /api/orders/[id]`, `DELETE /api/orders/[id]`, the bulk delete path, both
attachment routes and the acknowledgment upload. All refuse with 409
`archived_read_only`.

**What stays open:** restoring. On a standalone row that is PATCH
`{archived: false}` **and nothing else**; on a purchase it is the projects
route, which none of this touches. A group whose purchase is archived is
refused even that, because restoring a group was never its own act.

⚠ **THE WEBHOOK AND THE CRONS ARE EXEMPT**, because they do not come through
these routes. Shopify keeps sending updates for an archived purchase and those
must keep landing, so the rule is "no human edits", not "no writes".

**`/archive` is where archived work lives** (2026-09-16). Four tabs — All,
Shopify Orders, Custom Orders, Warranty Orders — with ONE LINE PER PURCHASE
showing its parts and the stage each stopped at, and one line per archived
custom job or warranty claim. Newest first by `archived_at`, undated last.
Restore is the only action: on a purchase it goes through the projects route
and brings every part back at the stage it stopped at, on a standalone row
through `PATCH /api/orders/[id]`.

⚠ **IT READS `allOrdersIncludingArchived`.** `allOrders` hides the groups of an
archived purchase, which is right everywhere else and wrong here. The projects
hub's Archived filter read `allOrders` and so listed archived purchases with no
parts at all; that filter is gone — the hub is active work.

**The modal shows everything and offers nothing** (2026-09-16). `archivedVia`
in `lib/data` is the question, and `lib/archived.ts` re-exports it, so the modal
hides exactly what the routes refuse. Gone: the claim chip, Edit order, archive,
restore, delete, re-decode, every stage move, Modify and Save on dates, the
tracking save, Save notes, and upload, delete, Report damage and Resubmit in the
panels. Still there: the tabs, the stage rail **disabled** (it is how you read
where the work stopped), notes and tracking as read-only fields, the attachment
list with Download, the damage reports, Activity, and Close. The header adds two
lines: **who handled it**, and **when it was archived** with restore named as
the way back.

⚠ **THE DATABASE ENFORCES IT** (2026-09-16, migration
`2026-09-16-orders-standalone-payment-and-archive.sql`).
`orders_archived_standalone_only` rejects `archived = true` on any
project-linked row, whoever writes it — a webhook, an import, a script, the
SQL editor. The routes keep their 422, so a caller is told why rather than
handed a constraint name.

**`archived_at` records WHEN** (2026-09-16), on `orders` and on `projects`. It
is set when something is archived and cleared when it is restored, so it is
non-null exactly while `archived` is true; re-archiving overwrites it and the
activity trail keeps the earlier ones. The three archive paths write it: the
projects route for a purchase, `PATCH /api/orders/[id]` and `/api/orders/bulk`
for a standalone row. **The database ties the two together**
(`orders_archived_at_matches`, `projects_archived_at_matches`, 2026-09-16): a row
is archived exactly when it carries a date. The one writer that set `archived`
without a date was `/api/shopify/orders`, deleted the same day (handoff item 15),
which is what made the constraint possible.

That is how SHO-1052 vanished on 2026-09-15 — archived as a project AND as
two groups, then restored as a project only. It showed in the projects hub
and not in cabinet orders, because the two read different tables. **A
project is the unit of archiving: archive it and both groups go, restore it
and both come back.** Standalone rows — custom jobs and warranty claims,
which have no project — keep order-level archiving.

**Money lives on the project.** `projects.total_price` for checkouts;
`orders.total_price` only for standalone custom jobs, enforced by a CHECK so a
project-linked row physically cannot carry one. Revenue is the sum of both, with
no overlap possible.

⚠ **SO IS THE PAYMENT STATUS, AND THE REFUND HOLD READS IT THERE** (2026-09-16).
`paymentRecordOf` in `lib/data` answers "whose payment status": the project for
a Shopify group, the row for a standalone one. The PATCH route's hold, the
acknowledgement — written to `projects.payment_hold_cleared_for`, so one covers
the whole purchase — the modal's refund banner, the work queue's "Refund
acknowledgment required", the table's payment pill and the production-complete
cron all go through it; on the client the store resolves every row once. Before,
each read the group's copy, which the webhook keeps equal to the project's with a
second, unchecked write, and a two-group refund had to be acknowledged twice.
**The group copy is gone** (2026-09-16): the webhook no longer writes it, the
backfill route writes projects, and `orders_payment_standalone_only` forbids
`payment_status`, `payment_hold_cleared_for` and `payment_hold_cleared_at` on a
project-linked row. All three, because a status and its acknowledgement are one
fact. Custom jobs and warranty claims keep all three on the row.

⚠ **THE OVERNIGHT PRODUCTION RUN HONOURS THE HOLD AND AN ARCHIVED PURCHASE.**
`productionAutoAdvanceSkip` in `lib/autoAdvance` is the one rule: a refunded and
unacknowledged purchase, an archived purchase, or a project that cannot be read
is not advanced. The cron lists what it skipped, with the reason, in its response
(so in `cron.log`), and the modal's "Moves to At cross dock on …" asks the same
function, so it never promises a move the cron will not make. If the projects
cannot be read, the cron advances nothing and answers 500.

## SLA — 24h soft, 48h hard

Two ideas, and the second is the one people miss:

- **Elapsed-time stages** ask "how long has this been sitting here". `New`
  measures from the order date, so bouncing an order back cannot reset it.
- **Missing-data stages** ask "is the thing that would let this move absent".
  An order can legitimately sit in production for six weeks — what is never
  legitimate is sitting there with no dates, because then nothing can advance
  it. Same for a hardware group with no tracking number.

Stages waiting on a third party — `Parts ordered`, `Shipped` — have **no rule**.
There is no field that would say when to stop worrying.

# 4. Why a row needs someone

One derivation, `lib/attention.ts`, read by the dashboard, the work queue and
the sidebar badges. **Nothing carries its own predicates**, because this
codebase's recurring failure is one rule written twice with a clause missing
from the second — it happened four times in six days before this existed.

Reasons: past SLA · due soon · blocked on missing data · unclaimed · payment
hold · acknowledgment missing · receipt missing.

## ⚠ `lib/requirements.ts` is the source for what a row still needs

Added 2026-09-08. One table keyed on `(type, stage)`. Each entry carries a
label, a remedy, a predicate, whether being unmet keeps an SLA clock running
(`clocks`), and — since 2026-09-09 — whether the SERVER refuses the
transition without it (`gates`).

⚠ **`clocks` AND `gates` ARE DIFFERENT QUESTIONS.** A delivery date at At
cross dock keeps a clock running and the route lets the move through without
it; a signed receipt runs no clock and the route refuses without it. The
modal disables its move button on `gates` and only `gates` — disabling on
every unmet requirement would be a client gate stricter than its server,
which is the failure this table exists to end.

⚠ **THREE FUNCTIONS, THREE QUESTIONS.** Reaching for the wrong one is subtle
and has already produced one near-miss:

| Function | Asks |
|---|---|
| `requirementsFor(order)` | what is the CURRENT stage waiting on |
| `dateControlsFor(order)` | is a date the thing you came here to TYPE |
| `typeEverRequires(type, id)` | does this type need it at ANY stage |

`dateControlsFor` exists because "required" and "is the next action" are not
the same: a custom job requires nothing by decision and still wants its
production dates recorded, and conflating the two left it with no field at
all. `typeEverRequires` exists because the tracking gate applies **whichever
direction you arrive from**, and the table lists `tracking_number` at the
stage BEFORE Shipped — so a current-stage question would silently stop
requiring it on a backward admin move from Delivered, which is exactly when
somebody is fixing a mistake.

⚠ **`lib/requirements.ts` KEEPS NO RUNTIME DEPENDENCY ON `lib/data`.** The
dev-only consistency check uses a lazy import for that reason, and
`typeEverRequires` resolves flows from the table's own keys rather than the
stage list. `REQUIREMENTS` is exhaustive over every `(type, stage)` — custom
lists all six of its stages with empty arrays — and the boot check fails if
that stops being true.

Before it, the same question was answered in FOUR places — `sla.ts`'s
`clockRuns`/`waitingFor`, `stageLogic.ts`'s `fieldsToClearOnBackwardMove`, the
PATCH gates, and `categories.ts`'s `trackingTargetStage`. Four shapes of one
fact.

**Deriving from it today:** `sla.ts` (`clockRuns` and `waitingFor` are overlaid
in `slaRuleFor`, so no caller changed), `attention.ts` (the two join-backed
reasons), the dashboard and the work queue.

**The PATCH gates: DONE 2026-09-15.** All four — acknowledgment-or-attachment,
production start date, tracking number, signed receipt — derive from the
table on the server, and `lib/stageGates.ts`'s client copy asks the same
line. Verified by enumerating every (type, from-stage) pair: **69 of 69
identical.** Do that for anything else migrated here; reading the diff is
not the same evidence.

⚠ **`gates` IS DESCRIPTIVE, NOT EXECUTABLE.** The production gate still reads
the request body: `requirementsFor` answers from the STORED row, but the
modal sends the date and the stage in one PATCH, so a fully table-driven
check would refuse the very request that satisfies it. The table can say a
requirement blocks a transition; it cannot say "and the request itself may
supply it". **Do not try to finish the job by removing that.**

**Not yet:** `fieldsToClearOnBackwardMove`. A behaviour change, to be argued
on its own.

⚠ **THREE STATES, NOT TWO.** `met`, `unmet`, `unknown`. Unknown is what a
join-backed requirement reports when nobody fetched the enrichment — and the
right response to it differs by surface. A QUEUE shows no reason, because one
that guesses sends somebody to redo finished work. A MODAL shows it as
outstanding with the move button disabled, because a person is looking straight
at it and a premature tick beside a live button is the worse error.

## Answering the joins: `POST /api/orders/enrichment`

Returns `{ackGreen, hasAttachment, hasProofOfDelivery}` per order, in **five
queries regardless of how many rows are asked for**. `lib/useOrderEnrichment.ts`
is the hook; the work queue, the dashboard and the modal all call it, so they
cannot disagree.

⚠ **It reimplements nothing.** The four-layer vendor chain is `resolveVendors`
and the green-and-not-stale verdict is `allVendorsGreen` — the same functions
the server gate calls. A second copy of either would mean the queue and the
gate disagreeing about whether an order can advance, and the queue is the one
people would believe.

⚠ **The last two have never appeared on a screen.** *(Fixed 2026-09-08 — see
above. Kept because the reasoning below is why the enrichment argument exists
at all.)* They need a join —
`order_acknowledgments` and `order_attachments` cannot be read off the row — so
`attentionFor` takes them through an optional `enrich` argument. **No caller
passes it.** Every call site in the dashboard and the work queue calls
`attentionFor(order)` with one argument, so those two reasons are unreachable:
built, documented, and never fired. Making them live needs a batch endpoint
rather than a per-row query, and it is item 1 on the remaining-work list.

⚠ **The buckets OVERLAP on purpose.** A purchase blocked for sixty hours counts
as blocked AND past-SLA AND needing attention. They are four questions about the
same rows, not a partition — making them exclusive would drop a row out of
"Blocked" the moment it also breached, which is when you most want to see it.

# 5. ⚠ Realtime — which tables publish, and why it matters

Four tables are in the `supabase_realtime` publication: **`orders`,
`projects`, `team_members`, `order_activity`.** Subscriptions live in
`lib/useRealtimeOrders.ts`, one channel each, wired in `lib/store.tsx`.

⚠ **PUBLISHED IS NOT DELIVERED.** Realtime sends a row only to a subscriber whose
ROLE MAY SELECT IT. The browser subscribes as `authenticated` — a 30-minute JWT
from `POST /api/realtime-token`, minted for signed-in sessions only — so every
published table needs a read policy for that role. `order_activity` was
published on 2026-09-15 with none: its only policy, `no_direct_access`, is
`false` for everyone, so no browser received a trail row until
`authenticated_read_all_activity` (SELECT, `true`) on 2026-09-30
(`migrations/2026-09-30-activity-readable.sql`). Writes stay refused. Only stage
moves and archiving add their trail row locally; every other row — notes, dates,
claims, overrides, anything a colleague did — appeared only on a refresh, and
that came to look normal. **Verify a realtime change with a second tab**, not by
listing the publication.

⚠ **`projects` WAS MISSING UNTIL 2026-09-15**, and the subscription had been
correct the whole time with nothing to receive. Because a Shopify
purchase's claim lives on the PROJECT, a claim taken by one person reached
nobody else's screen until they happened to refresh — which defeats the
entire purpose of claiming. Recorded as
`migrations/2026-09-14-realtime-projects.sql`.

⚠ **ADDING A TABLE TO THE PUBLICATION WITH NO SUBSCRIBER DOES NOTHING** and
looks like a fix. `order_attachments` is still absent. The client half now
exists — `lib/attachments` (2026-09-30), one shared list per order with
`refreshAttachments(orderId)` — so what remains is a subscriber that calls it on
a change, and a read policy for `authenticated`, without which a published table
delivers nothing (above). `lib/ackStatus` and `lib/attachments` both take
tickets — every request carries one and only the newest may write — so either
is the pattern (`ackStatus` since 2026-10-07; before, an older answer could
overwrite a newer one, proven 2026-09-30).

⚠ **THE ACTIVITY MERGE IS DEDUPED.** `moveStage` and friends append an entry
optimistically before the round-trip, so realtime delivering the server's
row would show the actor their own action twice. Matched on text AND time —
and `time` is a DAY string, so two identical texts on one day collapse to
one. Entry texts carry a stage and an actor name, which makes that unlikely;
dropping the optimistic append instead would put a round-trip in front of
every action's feedback.

⚠ **A REFUSED OPTIMISTIC CHANGE IS UNDONE ON ONE RECORD, FIELD BY FIELD.**
`moveStage`, `archiveOrder`/`unarchiveOrder` and `updateTeamMember` apply
their change locally before the round-trip. On a refusal each puts back only
the fields that call changed, and only where nothing has written them since —
`undoFields` in `lib/store.tsx`, which the archive pair mirrors by hand.

Until 2026-09-16 `moveStage` and `updateTeamMember` restored a snapshot of the
whole array taken inside a setState updater. React fills such a snapshot in
only when it runs the updater, so: `moveStage` looked its row up in an empty
array and never mirrored the backward-move clearing on a store that had
updated recently; a refusal restored the array as of the next render, undoing
any other row's change that landed meanwhile, a colleague's realtime edit
included; and a refusal that beat the render restored `[]`. **Do not
reintroduce a snapshot.**

**healthchecks.io**, deliberately off-box so a box outage cannot silence its own

## ⚠ `webhook_events` — webhook outcomes that survive a deploy

Added 2026-09-15. `logWebhook` wrote to `console.warn` and nowhere else, in
a container replaced on every deploy. That is how the SHO-1051 deletion bug
survived two attempts: the handler reported `removed` twice while deleting
nothing, and the only evidence was log lines one more deploy would have
erased.

Every call site now also writes a row. The insert is **not awaited** — a
handler must not fail or slow because logging failed, and Shopify retries on
a non-2xx, so a logging error would become a redelivery loop for a webhook
that already did its work. It falls back to stderr if the write fails,
because a log table that quietly stops recording is the same shape as the
bug it replaces.

```sql
select outcome, topic, order_id, shopify_id, detail, created_at
from webhook_events order by created_at desc limit 20;
```

⚠ **The account holds eleven checks. Four watch anything.** The other seven are
strays from an earlier setup, each with a 365-day period, so they report "up"
forever. They are listed for deletion and ignored **by name** in the in-app
panel — not merely left ungrouped, because ungrouped is where a genuinely new
check would land.

## ⚠ What the ping path guarantees

- **`run-cron.sh` validates the URL shape before pinging.** A malformed entry
  goes to stderr, which cron mails.
- **A non-2xx ping is logged.**
- ⚠ **The job's exit status is untouched by either.** Monitoring must never
  break the thing it monitors.
- **The in-app panel is a window onto the alarm, never the alarm.** If the box
  is down, so is the OMS and so is the panel.

The first two are what the six-day monitoring outage of August 2026 produced.
The third was already the design and stays it — the bug was never the exit
status, it was that the ping path could not report on itself. **The incident
itself is in `OPERATIONS` §9**, which is where history lives.

# 7. The build — what it fetches, and what it must not

`kamal deploy` builds the image on the box: `npm ci --frozen-lockfile`, then
`next build` (Turbopack), then the standalone output. Everything that build reads
from outside the repo is a way a deploy can fail for a reason no commit
contains.

## The brand fonts are served from the repo (2026-10-01)

`app/fonts/` holds DM Sans (weights 300–600, upright) and Cormorant Garamond
(400–600, upright and italic), Latin and Latin Extended, loaded by
`next/font/local` in `app/layout.tsx` under the same `--font-sans` /
`--font-serif` variables `globals.css` and Tailwind have always read — nothing
else had to change.

⚠ **WHY.** They were `next/font/google`, which downloads both fonts from Google
while the image builds. On 2026-10-01 the deploy of `e027ee9` failed inside that
download (Turbopack: "next/font/google queries have exactly one entry"), and the
same commit built cleanly on a retry. Same commit, and the same unchanged
lockfile installed by `npm ci --frozen-lockfile`, so the one thing that differed
was what Google answered. With these files the build fetches nothing — proven by building
in a sandbox that cannot reach Google: the old layout failed there on both
fonts, the new one built, on the same Next (16.2.12).

**What the files are.** Rebuilt from Google's own sources, `google/fonts` @
`9710da1eacb3be272583c3224dcb70f9da6eadbb` (2026-09-30), by
`scripts/build-brand-fonts.py`, which says how to get those sources and gives
byte-identical files on every run. Each font's weight axis is narrowed to exactly
the weights the layout used to ask Google for. Against the originals at each of
those weights: no glyph's shape or width changed, and no point moved more than
2/1000 of an em — rounding. ⚠ **DM Sans's optical-size axis is PINNED AT ITS
DEFAULT, 9**, on the assumption that Google pinned it there too for a request
that never mentioned it (the request was `DM+Sans:wght@300;400;500;600`). That
is to be checked by comparing a screenshot of the same screen before and after
the first deploy. Licence: the SIL Open Font License, which allows bundling, and
travels with the files (`app/fonts/OFL-*.txt`).

**To add or change a weight:** change the script's range and the layout's
`weight` together, rebuild, and commit the fonts with both.

## `xlsx` is pinned to 0.20.3 (2026-10-07)

`xlsx` installs from `https://cdn.sheetjs.com/xlsx-0.20.3/xlsx-0.20.3.tgz` —
`package.json` and the two lockfile lines that named it. Until 2026-10-07 it came
from `xlsx-latest/xlsx-latest.tgz`: npm records a tarball's integrity hash in
the lockfile, so the first dependency rebuild after SheetJS published a new
"latest" would have failed `npm ci`, for a reason no commit contained. Before
pinning, the box hashed both files: the lockfile expected 0.20.3 with
`sha512-oLDq3jw7…`, and the versioned URL and "latest" both served exactly those
bytes — SheetJS had not released since, and the pin installs the same file.
**To upgrade:** change the version in both files' URLs and run `npm install`;
the lockfile takes the new hash, and `npm ci` checks it on every build.

## Next.js 16.4.0, pinned exactly (2026-10-07)

`next` and `eslint-config-next` are `"16.4.0"` with no caret, so a framework
upgrade is always a decision, never a side effect of `npm update`. Moved from
16.2.12 for three critical security fixes after it (Aug 25: remote code
execution via the image optimizer's AVIF handling, and one on Windows hosts;
Sep 22: remote code execution in `next/og`'s `ImageResponse`); 16.4.0, a day
old, was chosen over the patch-only 16.3.8 (Garrett). Every other dependency
went to its newest release within its current major — `@supabase/supabase-js`
2.43 → 2.117, React 19.1 → 19.3 among them. `npm audit --omit=dev`: 0. The
image runs on `node:22-alpine` (supported to April 2027).

⚠ **`npm run build` FAILS IN A PLAIN SHELL, AND THAT IS NOT A BUG.** Collecting
page data evaluates route modules, and `lib/supabase` throws without
`SUPABASE_URL`. The image's build stage mounts the real secrets for exactly that
step. To build outside kamal — an uncommitted change, say — `docker build` with
`--secret id=NAME,env=NAME` for every id the Dockerfile mounts, the values
loaded from `.env.kamal` in a subshell (handoff item 38 has the command).
